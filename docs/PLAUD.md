# Plaud 전사·정리본 가져오기

데스크톱 **0.6.2-achmage.4**부터 기본 경로는 기존 Plaud 결과를 활용합니다.

1. **전체 기록 → Plaud에서 가져오기**에서 연결하고 녹음을 선택합니다.
2. 기본값 **기존 Plaud 전사로 정리 (추천)** → **가져와서 정리 준비**를 누릅니다.
3. raw 전사 전체, 발언별 화자·시각, 녹음 날짜를 가져옵니다. Plaud 정리본은 **AI 생성 보조 자료**로 자동 첨부합니다. raw 전사가 기준이며, Plaud 정리본이 Achmage 최종 문서를 대체하지 않습니다.
4. 자동으로 열린 준비 창에서 필요한 맥락·파일·링크를 더하고 **이 자료로 정리 시작**을 누릅니다. 기존 모델 설정과 Achmage 정리 파이프라인을 사용합니다. 가져오기만으로 유료 AI를 실행하지 않습니다.

**원음도 보관하기**를 체크하면 전사 인계 후 원음을 백그라운드로 내려받아 재생용 오디오를 준비합니다. 원음 실패·중단은 이미 가져온 전사·정리본을 취소하지 않습니다. 가져오기 내역에 상태를 표시하며 같은 Plaud 녹음을 다시 선택해 원음 보관을 재시도할 수 있습니다. 새로 녹음을 이어서 만든 재생 파일을 뒤늦은 다운로드가 덮어쓰지 않습니다.

**원음으로 새로 전사**는 별도 선택입니다. 기존 로컬 ASR 대기열을 사용하며 긴 녹음은 오래 걸릴 수 있습니다. Plaud 전사를 가져온 기록과 별도 기록이므로 기존 전사·편집 결과를 덮어쓰지 않습니다. Plaud에 전사가 없으면 이를 안내하며, 자동으로 느린 재전사를 시작하지 않습니다.

동일 모드로 다시 가져오면 사용 가능한 기존 기록을 재사용합니다. 삭제·휴지통 처리된 기록은 되살리지 않습니다. Plaud 정리본 조회에 실패한 경우에도 raw 전사를 사용할 수 있으며, 준비 창에 안내하고 필요하면 정리본을 직접 첨부할 수 있습니다.

## 작업 취소와 알림

- 휴지통 이동·영구 삭제 시 해당 가져오기를 취소하고 알림을 숨깁니다.
- 취소한 ASR이 정리되는 동안에도 알림 닫기가 가능합니다. 알림 숨기기는 실제 작업 종료나 원본 삭제와 별개입니다.
- 영구 삭제는 해당 작업의 파일 쓰기 종료를 기다립니다.
- 이전 버전에서 이미 삭제한 기록에 남은 알림도 다음 실행 시 숨깁니다.

## 연결과 저장

공식 HTTP MCP `https://mcp.plaud.ai/mcp`의 `list_files`, `get_file`, `get_transcript`, `get_note`를 사용합니다. `get_transcript`의 모든 페이지를 확인하고, 시각은 공식 transaction 응답의 밀리초 단위를 유지합니다. 미완성·순서 변경·반복 페이지는 완성된 전사로 저장하지 않습니다.

OAuth PKCE S256와 일회성 state, loopback callback을 사용합니다. 인증 정보는 로컬에만 저장하며 safeStorage가 가능하면 암호화합니다. GitHub에 개인 녹음·전사·자격증명을 올리지 않습니다. 원음은 Plaud가 제공한 HTTPS 저장소 주소에서 스트리밍으로 받습니다. 파일 한 개 최대 10GB, 미완성 다운로드는 전사 대기열에 등록하지 않습니다.

이 연결은 Plaud의 새 전사 요청이나 원격 수정·삭제를 하지 않습니다. Plaud 자체 자동 전사를 원하지 않으면 Plaud 앱의 새 녹음 자동 요약 설정도 꺼야 합니다. 기존 Plaud 전사를 쓰는 경로는 이미 수행된 Plaud 전사의 비용을 없애는 기능이 아닙니다. 현재 모바일 웹앱에는 이 기능이 없습니다.

## 검증

- 실제 2시간 18분 녹음을 읽기 전용 MCP로 격리 프로필에 가져와 발언 913개·화자·Plaud 정리본 첨부 확인. 직접 MCP 수집 시험은 10초 이내, 실제 설치본에서 버튼 클릭부터 정리 준비 창까지는 약 16.6초였습니다. 원음 다운로드·ASR·LLM 정리는 실행하지 않았습니다. 서버/네트워크에 따라 시간은 달라집니다.
- TypeScript, 가져오기·Plaud·휴지통·정리 관련 회귀 테스트 및 Electron 준비 창 인계 확인. YouTube 정리 내용 생성 로직은 유지하며, 구독 AI 실행 대기열은 아래 병렬 정책을 적용합니다.
- 최종 AI 정리 품질과 Windows/macOS 실기기는 이번 검증에서 새로 시험하지 않았습니다.

## 구독 AI 병렬 정리

서로 다른 기록의 텍스트 정리는 각각 독립된 구독 CLI 세션으로 실행합니다. 임의의 2건 제한은 없습니다. 같은 기록의 작업은 순서를 지키며, 전체 모델 유지보수 작업은 진행 중인 요청이 끝난 뒤 실행합니다. 로컬 ASR 대기열은 별개입니다. 구독 AI 정리는 다른 기록의 녹음이나 ASR 메모리 정책 때문에 중단하지 않습니다.

순간적인 요청 제한(429/rate limit)은 응답 본문이 나오기 전에만 5초·15초·30초 간격으로 최대 3회 재시도합니다. 구독량 소진·인증 실패·이미 일부 본문을 받은 실패는 자동 반복하지 않습니다. 실제 제공자 처리 속도와 계정 한도는 그대로 적용됩니다.

전체 기록과 폴더 목록의 각 행에 진행 단계와 스킨 강조색 테두리 효과를 표시합니다. 요청 대기는 정적인 상태로, 완료·중단은 효과를 제거하고 실패·확인 질문은 문구로 표시합니다. OS 동작 줄이기 설정을 따릅니다. 상단에는 진행 기록 수를 표시하고 오류의 재시도·알림 닫기는 유지합니다.

검증: 서로 다른 6개 작업의 동시 시작, 같은 기록 순서, 독립 취소·삭제, 일시 제한 재시도 및 응답 중복 방지. Electron에서 3개 행의 독립 진행·완료·실패·새로고침·동작 줄이기를 시험했습니다. 실제 구독 AI를 여러 건 호출한 속도 비교는 수행하지 않았습니다.
